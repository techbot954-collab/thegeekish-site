Someone made Doom run through SQL because of course they did

CedarDB's SQLDoom project turns the original Doom's game logic and renderer into database queries, with Python only handling input, timing, and display.

JP
Updated October 2, 2026

Concise Geekish brief based on Ars Technica and CedarDB.

What happened

Ars Technica covered SQLDoom, a CedarDB project by Lukas Vogel that renders Doom through a database. The CedarDB write-up says the original game's logic and renderer run as SQL queries while a Python client handles keyboard input, timing, and showing the bitmap.

The project claims the game loop runs at the original 35 frames per second, with SQL producing the complete frame buffer. Ars notes that the implementation uses about 1,300 lines of SQL across 89 common table expressions for rendering.

Why it matters

This is mostly delightful engineering mischief, but it also shows how far modern databases and query planners can be pushed when game state becomes relational data.

The joke is that running Doom in strange places is a rite of passage. The useful lesson is that some systems problems become surprisingly expressive when you treat entities, state, and rendering steps as tables and joins.

Quick takeaways

  • SQLDoom uses SQL for game logic and rendering, with Python only as the client shell.
  • CedarDB says deathmatch works and that users can try the shareware episode through its demo setup.
  • The project is less "good idea" than proof that databases can be wonderfully weird machines.
